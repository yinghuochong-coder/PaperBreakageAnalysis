## 目的与可观察结果

在 M6-01/M6-02 编码前形成可审查、版本化且可机器检查的算法验收合同。合同必须区分已确定的标签/评估/制品完整性规则和仍需业务、数据或目标硬件负责人批准的数值；缺少冻结数据集或批准阈值时，门禁必须明确为 `blocked/not-approved`，后续实现只能标记为原型。

## 范围

### 范围内

- 断纸、正常纸幅、非断纸扰动和不可判定样本的标签定义；
- 数据集来源、拆分、防泄漏、标注、校验和冻结要求；
- 事件级召回率、精确率、每相机小时误报率、检测延迟的计算规则；
- 四路 60 fps 理论吞吐入口及目标机单帧延迟、CPU、内存预算的待批准字段；
- 传统视觉无外部模型时及以后引入模型文件时的来源、版本、许可证和 SHA-256 规则；
- 门禁审签、缺口清单、模板和 CTest 静态一致性检查。

### 范围外

- M6-01 插件接口、生命周期、ABI 或装载实现；
- M6-02 传统视觉算法、阈值调参、模型研发或推理依赖；
- M6-03 候选确认/降级和 M6-04 UI；
- 生成、复制、标注或提交生产图像；
- 代表业务、算法、数据或硬件负责人批准指标。

## 当前基线

- 路线图 DEC-006 明确正式算法、阈值和数据集尚未给定，M6-00 是最晚决策点。
- 仓库没有算法数据集、冻结清单、标注指南、评估报告或模型制品；现有 `paperbreak_algorithm_mock` 只服务 M5 事件链。
- 已知目标最多四台 `MV-CS020-60GM`，既有配置/真机记录使用 60 fps，但实际生产 ROI、像素格式和目标工控机 CPU/内存预算未给定。
- 工作树开始时干净；本任务不修改模块边界或生产代码。

## 前置条件与假设

- 数据集图像可存于受控外部存储，仓库只保存不含敏感原图的版本化 manifest、摘要和评估报告。
- 质量门禁以事件为主要计量单位；帧级结果只用于诊断，不能用类别不平衡的帧准确率替代事件召回和运行时误报率。
- 若每路 60 fps 均提交算法，四路入口为 240 frame/s；实际降采样或跳帧策略必须在 M6-03 另行批准，不能在 M6-00 静默降低吞吐目标。
- M6-02 计划中的传统视觉实现默认不需要外部模型文件；若实现引入背景模板、标定、权重或其他二进制制品，必须按同一制品策略登记并冻结。

## 设计说明

`docs/validation/m6-00/algorithm-acceptance-baseline-v1.json` 是门禁状态的机器可读单一来源。它只记录从现有需求可确定的工作负载和评估语义，所有需外部批准的数值保持 `null`，并列入 `blockingItems`。数据集 schema 和模板独立版本化；批准清单必须是 `frozen`，包含拆分、来源、标注、独立性和 SHA-256 信息。Markdown 说明用于人工评审，不能覆盖 JSON 的 `not-approved` 状态。

### 线程和队列

不适用。本任务只新增文档、JSON 合同和配置期 CMake 校验，不创建运行时线程、队列或缓存。

### 持久化与恢复

- 基线、schema、模板和审签记录均在 Git 中版本化；数据集原图不进入仓库。
- 冻结数据集以 manifest 版本和 SHA-256 根摘要识别；任何内容变化必须生成新版本，禁止原地覆盖。
- 回滚只撤销本任务文档和测试接线，不触碰生产数据、配置、事件目录或数据库。

### 错误和降级

- 缺少批准 manifest、质量阈值、目标机预算或审签时，门禁为 `blocked`，`prototypeOnly=true`。
- 模板、零摘要和未签字记录不得被解释为验收证据。
- M6-01/M6-02 若在门禁解除前开展，只能以原型身份交付，不得宣称正式算法通过验收。

## 验证计划

### 自动化测试

- 解析基线、schema 和模板 JSON；
- 校验 schema/version、门禁状态、`prototypeOnly`、四路 60 fps/240 frame/s 算术和五项阻塞清单；
- 校验模板始终为 `draft`，不能冒充冻结批准数据集。

### 构建与测试命令

```powershell
cmake --preset local-windows-vs2026-debug
cmake --build --preset local-windows-vs2026-debug
ctest --preset local-windows-vs2026-debug -R m6_00_acceptance_baseline
ctest --preset local-windows-vs2026-debug
git diff --check
```

本任务不改变发布二进制或生产依赖，不要求 Release 构建；若配置接线影响全量构建，则仍以 Debug `/W4 /WX` 全量构建验证。

### 人工或硬件验证

- 环境：批准的数据集存储、标注/复核人员、目标工控机、最多四台目标相机或等价回放负载。
- 步骤：冻结数据集并生成摘要；填写质量阈值；在固定 ROI/像素格式/帧率下评估；记录目标机延迟、吞吐、CPU、内存；四方审签。
- 预期：冻结测试集不可用于调参；质量和性能置信区间满足批准阈值；所有制品可按 SHA-256 复核。
- 证据位置：`docs/validation/m6-00/` 中批准的 manifest、审签记录和可复现评估报告引用。
- 当前状态：未执行。仓库没有数据集、批准阈值和目标硬件预算，不能声明通过。

## 决策记录

- DEC-001：主要业务指标采用事件级召回、精确率、每相机有效小时误报率和检测延迟；帧准确率只作诊断，避免大量正常帧掩盖漏报。
- DEC-002：数据拆分按生产卷/采集会话/真实事件分组，禁止相邻帧跨 development/validation/test，防止时间相邻泄漏。
- DEC-003：在没有外部批准事实时不填建议阈值；门禁明确阻塞，但提供完整合同和解除步骤。
- DEC-004：传统视觉代码本身以算法语义版本、源码提交和配置摘要追踪；任何外部模型/背景/标定制品另以来源、许可证、版本、大小和 SHA-256 追踪。

## 意外发现

- 既有单相机 M3 真机记录证明约 60 fps 采集能力，但不能推出四路算法吞吐、生产 ROI 或算法 CPU 预算。
- 现有仓库仅有 M5 mock detector 测试数据，属于事件链构造数据，不能当作断纸算法验收数据集。
