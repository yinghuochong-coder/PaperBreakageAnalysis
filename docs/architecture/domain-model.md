# 领域模型、时间与版本语义

## 1. 文档目的

本文是边缘系统跨模块、配置、IPC、事件文件、SQLite 和上位机通信共同使用的领域语言基线。后续实现可以增加内部字段，但不得改变本文中标识符、状态、时间和版本的含义；需要改变时，必须先更新本文和受影响的 schema/协议版本。

关键词“必须”“不得”“应”“可以”表示规范性约束。

## 2. 标识符

### 2.1 标识符总则

- 标识符是不可变的 UTF-8 ASCII 文本，比较时区分大小写；
- 标识符不得包含密码、IP、文件绝对路径或可变显示名称；
- 数据库自增主键、内存地址、相机句柄和数组下标不得作为跨边界业务标识；
- 对外接口把标识符视为不透明字符串，不得通过解析其中的时间或顺序决定业务正确性；
- 创建成功后不得复用已使用的标识符，包括已拒绝、超时、删除或上传失败的对象。

### 2.2 `CameraId`

`CameraId` 是生产线位置对应的稳定逻辑相机编号。首期合法值为：

| Camera ID | 需求示例含义 |
| --- | --- |
| `CAM01` | 第一逻辑相机槽位（需求示例为压榨部入口） |
| `CAM02` | 第二逻辑相机槽位（需求示例为压榨部出口） |
| `CAM03` | 第三逻辑相机槽位（需求示例为烘干部入口） |
| `CAM04` | 第四逻辑相机槽位（需求示例为卷取部） |

首期规范形式为正则 `^CAM0[1-4]$`。实际位置名称是可配置的 `displayName`，不属于 ID。

必须区分：

| 概念 | 含义 | 是否可变 |
| --- | --- | --- |
| `CameraId` | 业务使用的逻辑槽位 | 配置迁移前稳定 |
| `deviceSerialNumber` | 厂商设备序列号，用于绑定 | 更换实体相机时可变 |
| `ipAddress` | 当前网络地址 | 可变，不参与业务身份 |
| `deviceHandle` | 适配器内部运行时句柄 | 短生命周期，不得跨适配器 |
| `cameraFrameNumber` | 相机提供的帧号 | 可能重置、跳变或不可用 |
| `sequenceNumber` | 本次相机会话内由服务分配的接收序号 | 仅在该会话中递增 |

业务模块、事件和配置引用 `CameraId`。只有相机绑定/诊断层可以用序列号、IP 和厂商信息寻找实体设备。

### 2.3 事件 ID

`EventId` 在事件首次进入 `Candidate` 时由服务本地生成，即使工控机离线也不依赖中心服务。规范文本为：

```text
EVT-xxxxxxxx-xxxx-7xxx-yxxx-xxxxxxxxxxxx
```

其中 UUID 部分使用 RFC 9562 UUIDv7 的小写规范形式，`y` 为 `8`、`9`、`a` 或 `b`。示例：

```text
EVT-019870f2-6c80-7a31-9b52-6e3b9ca1d88f
```

生成和使用规则：

1. 生成器必须使用 UUIDv7 的时间字段与高质量随机位；同一进程同一毫秒内维持单调生成；
2. 本地数据库对完整 `EventId` 建唯一约束，发现碰撞时重新生成并记录 `SYS_ID_COLLISION`；
3. `EventId` 是全局事件身份；上位机对其建立全局唯一约束，并可在幂等键中同时包含 `machineId` 用于路由和碰撞诊断，不得只用目录日期、序号或事件时间去重；
4. UUIDv7 的时间部分仅用于大致排序，不是权威 `candidateTime`，系统时间回拨也不得改变或重发已有 ID；
5. 事件的确认、拒绝、超时、恢复、复核、导出和上传始终保留同一个 `EventId`；
6. 事件目录可以包含可读时间前缀，但必须包含完整 `EventId`，且身份只由 ID 决定。

### 2.4 其他标识符

| 名称 | 语义 |
| --- | --- |
| `MachineId` | 单台边缘工控机的已配置稳定 ID；设备重装恢复配置时应保留 |
| `ProductionLineId` | 生产线业务 ID；不得从主机名或 IP 临时推导 |
| `RequestId` | 一次 IPC/网络请求及其响应的关联 ID；重试幂等请求时保持不变 |
| `CorrelationId` | 贯穿命令、事件、写入和上传的诊断关联 ID |
| `UploadTaskId` | 一个持久上传工作项的 ID，形式为 `UPL-` 加 UUIDv7 |
| `LogicalFileId` | 事件内文件的稳定逻辑 ID，不是绝对路径 |

## 3. 核心术语

### 3.1 帧与触发

| 术语 | 定义 |
| --- | --- |
| 帧（Frame） | 某个 `CameraId` 的一次图像采集结果及其不可变元数据 |
| 完整帧 | 像素数据、尺寸、格式和必要元数据均满足处理契约的帧 |
| 不完整帧 | 相机或传输报告缺失/截断的数据；可用于诊断，不得伪装为完整算法输入 |
| 检测结果（Detection Result） | 算法针对一帧给出的异常、置信度、原因、版本和耗时等结果 |
| 触发（Trigger） | 导致状态机评估候选的算法、人工或外部信号记录；触发不是事件本身 |
| 关键帧（Key Frame） | 依据角色从事件窗口选出的引用或派生图像；不能替代原始事件片段 |

### 3.2 事件与状态

事件（Event）是由一个不可变 `EventId` 标识的 `EventAggregate`，聚合触发、状态转换、多相机前后窗口、关键帧、持久化、复核和上传状态。状态定义如下：

| 状态 | 定义 | 是否已有 Event ID | 是否保护缓存 |
| --- | --- | ---: | ---: |
| `Idle` | 当前没有待评估异常；这是状态机状态，不是事件 | 否 | 否 |
| `Suspicious` | 单帧或短暂异常，尚未满足候选阈值；这是暂态观察，不创建事件 | 否 | 否 |
| `Candidate` | 已满足候选阈值；立即创建事件、分配 ID 并保护前后缓存 | 是 | 是 |
| `Confirmed` | 候选满足连续帧、批准的算法或外部确认条件 | 是，同一 ID | 是，直至窗口封闭 |
| `Rejected` | 候选被判定为误报；记录仍保留用于审计和指标 | 是，同一 ID | 按已接受窗口完成/释放 |
| `Timeout` | 候选在截止时间前没有得到确认或拒绝 | 是，同一 ID | 按已接受窗口完成/释放 |

`Confirmed`、`Rejected` 和 `Timeout` 是候选判定终态，不等同于文件写入、人工复核或上传状态。不得用“正式事件”表示另一个新对象；在面向操作员文本中，“正式事件”专指状态为 `Confirmed` 的同一事件。

事件还具有相互独立的正交状态：

| 状态维度 | 示例值 | 说明 |
| --- | --- | --- |
| `decisionState` | Candidate/Confirmed/Rejected/Timeout | 检测判定 |
| `persistenceState` | Collecting/Writing/Committed/Incomplete/Corrupt | 事件证据写入 |
| `reviewState` | Unreviewed/Acknowledged/Reviewed | 人工处置 |
| `uploadState` | NotQueued/Queued/InProgress/Succeeded/Failed | 汇总显示；真实工作项在 `UploadTask` |

任何接口必须注明返回的是哪个状态维度，不能只返回含糊的 `status`。

### 3.3 候选合并

- 第一次从 `Suspicious` 进入 `Candidate` 时创建事件；
- 同一活跃窗口内或 `mergeGap` 内的新触发追加到该事件的 `triggers`，扩展窗口但不创建新 ID；
- 只有当前事件窗口已封闭且新触发不满足合并规则时才创建新事件；
- 合并不得丢失原始触发相机、帧号、时间、原因和置信度；
- 事件版本每次状态或聚合内容变化时递增。确认/拒绝命令必须携带期望事件版本；重复同一命令幂等，过期的不同命令返回 `EVENT_VERSION_CONFLICT`。

### 3.4 上传任务

`UploadTask` 是将一个确定的元数据对象、清单、关键帧或文件分块可靠交付给上位机的持久工作项，不是事件状态。

- 一个事件可以有多个上传任务；
- 重试沿用相同 `UploadTaskId` 和 `RequestId`，不得创建重复事件；
- 幂等键至少由 `machineId`、`eventId`、`logicalFileId`、`chunkIndex` 和内容校验值组成；
- 任务至少区分 `Queued`、`InProgress`、`RetryWait`、`Succeeded`、`PermanentFailed`；
- `retryable=true` 只表示允许受限重试，不允许无界重试；
- 网络离线时任务保持持久状态，本地检测和事件保存继续。

## 4. 时间语义

### 4.1 三类时间

| 类型 | 来源 | 必须用于 | 不得用于 |
| --- | --- | --- | --- |
| `MonotonicTime` | `std::chrono::steady_clock` | 超时、退避、性能耗时、帧接收排序、事件前后窗口、合并间隔 | 用户展示、目录日期、跨进程/重启比较、外部序列化 |
| `WallClockTime` | `std::chrono::system_clock` | 审计、日志、IPC、事件清单、目录分组和用户展示 | 计算超时、持续时间和活动窗口 |
| `CameraTimestamp` | 厂商设备时钟 | 设备诊断、帧关联；只有同步质量经验证后才用于多相机对齐 | 作为唯一事件时间或替代工控机接收时间 |

`Duration` 是两个同一单调时钟点的差值，使用明确单位的整数或 `std::chrono` 类型。配置字段必须在名称中带单位，例如 `postEventMs` 或在 schema 中声明单位，禁止无单位裸数。

### 4.2 帧与事件时间

每帧至少记录：

- `receivedMonotonicTime`：工控机接收的单调时间；
- `receivedWallClockTime`：同一接收点附近采样的墙上时间；
- 可选 `cameraTimestamp`、原始计时单位和 `cameraTimestampQuality`。

每个已创建事件至少记录：

- 候选、确认（若有）、窗口开始和结束的单调时间，供本进程正确执行窗口；
- 对应墙上时间，供清单、数据库和 UI 使用；
- `clockQuality` 和发生过的时间跳变摘要。

单调时间只在拥有它的进程生命周期内有效，不写入可供下次启动直接比较的协议或持久格式。崩溃恢复根据已持久化帧索引、墙上时间、序号和恢复状态重建事实，不拿上次进程的 `steady_clock` 数值继续计时。

### 4.3 外部时间格式和时区

JSON、IPC、事件清单、审计导出和网络协议的规范输出统一为 UTC RFC 3339，固定三位毫秒：

```text
2026-07-30T05:47:00.123Z
```

规则：

- 输出必须使用 `Z`，不得省略时区，也不得输出未标注的本地时间；
- 输入可以接受等价的 `Z` 或显式 `±HH:MM` 偏移，校验后立即归一化为 UTC；
- 不接受时区缩写（如 `CST`）、本地化日期、无偏移时间或闰秒 `:60`；
- SQLite 物理列可以使用 UTC Unix epoch 毫秒整数以便排序，但 schema 必须明确单位，API 输出仍转换为上述格式；
- UI 可以显示配置的工厂本地时区，例如 `2026-07-30 13:47:00.123 +08:00`，并应同时显示偏移；本地展示值不得参与 ID、冲突检测或幂等判断；
- 目录可以按配置的工厂本地日期分组，但完整 `EventId` 才是目录身份，夏令时或时间回拨不得覆盖已有目录。

### 4.4 系统时间跳变和质量

`clockQuality` 至少支持 `Unknown`、`Synchronized`、`Degraded`、`JumpDetected`。健康监测通过比较墙上时间增量与单调时间增量识别显著跳变，阈值由后续配置 schema 定义。

发现跳变时必须：

1. 继续使用单调时间执行当前超时、窗口和退避；
2. 产生 `SYS_TIME_JUMP_DETECTED` 报警/错误记录；
3. 记录检测时的旧/新墙上时间差和单调时间，但不记录敏感信息；
4. 将受影响事件的 `clockQuality` 标为 `JumpDetected`；
5. 不修改已有 `EventId`、事件顺序号或已提交清单。

## 5. 版本语义

### 5.1 独立版本轴

| 版本 | 范围 | 规范载体 | 演进规则 |
| --- | --- | --- | --- |
| `configSchemaVersion` | 配置文档字段、类型和语义 | 配置根对象 | 每个已发布 schema 变更递增正整数；旧版经显式、可测试迁移后加载 |
| `configRevision` | 某台机器配置内容的并发修订 | 配置根对象和审计记录 | 服务提交成功后严格递增；写命令使用 expected revision 比较交换 |
| `ipcProtocolVersion` | 本机 IPC 消息契约 | 每条 IPC 消息 | 首期为 `1`；不兼容变更递增，新增可选字段保持兼容 |
| `uplinkProtocolVersion` | 上位机线上协议 | 握手/消息 | 与 IPC 独立；具体首版和协商规则在 M8-00 决定 |
| `eventSchemaVersion` | `manifest.json` 结构和字段语义 | 每个事件清单 | 每个已发布 schema 修订递增；已提交事件不原地改写 |
| `databaseSchemaVersion` | SQLite 表、索引和约束 | `PRAGMA user_version` | 每次迁移严格递增，迁移在事务中执行并有恢复/备份 |

算法版本、软件版本、NVMe 块格式版本和文件内容版本是另外的版本轴，不得借用上表任一计数器。

### 5.2 配置版本

配置根对象必须至少包含：

```json
{
  "configSchemaVersion": 1,
  "configRevision": 42,
  "modifiedAt": "2026-07-30T05:47:00.123Z"
}
```

- `configSchemaVersion` 回答“如何解释字段”，`configRevision` 回答“这是第几次已接受的内容修改”；
- `modifiedAt` 仅用于审计，不用于解决冲突；
- 服务是 `configRevision` 的唯一分配者，客户端提交 `expectedConfigRevision`；
- 内容没有变化的幂等重试返回原修订，不重复递增；
- 待重启字段可以随新修订持久化，但必须分别报告 `storedConfigRevision` 和 `effectiveConfigRevision`；
- 事件清单同时记录触发时生效的 `configSchemaVersion` 和 `configRevision`，不得使用含糊的单一 `configVersion`。

### 5.3 协议版本

- 收到未知更高 `ipcProtocolVersion` 时返回 `IPC_PROTOCOL_VERSION_UNSUPPORTED` 并关闭或限制该会话，不得猜测解析；
- 同一版本内接收方必须忽略明确允许扩展位置中的未知可选字段，但未知命令、必需字段缺失或字段类型错误仍是协议错误；
- 不兼容的字段改名、删除、语义改变、帧格式改变或必需字段增加必须提升协议版本；
- 上位机协议在 M8-00 独立定义；不得因为 IPC 升级而同步提升上位机协议，反之亦然。

### 5.4 事件 schema 版本

- 新事件只使用当前批准的 `eventSchemaVersion`；
- 读取器必须有明确支持范围；未知更高版本返回 `EVENT_SCHEMA_UNSUPPORTED`，不得部分解析后宣称完整；
- 已提交事件目录是不可变证据。读取旧版时在内存中适配；若必须导出新版，生成新的派生导出物并保留来源版本；
- 新增、删除、改名或改变字段语义均需发布新版 schema；是否兼容由版本说明和测试决定，不能仅凭 JSON 可解析判断；
- 上传清单携带事件自身版本，不能用当前软件版本代替。

### 5.5 数据库 schema 版本

- `databaseSchemaVersion` 只表示 SQLite 物理/逻辑 schema，不表示事件或配置格式；
- 每个版本都有从上一受支持版本升级的迁移和测试，禁止跳过未知版本；
- 升级前按策略备份，迁移失败返回 `DATABASE_MIGRATION_FAILED`，服务进入明确降级或启动失败状态；
- 应用程序不得自动降级数据库；需要回滚软件时使用批准的兼容版本或已验证备份；
- 目录/数据库对账不得修改已提交事件的 `eventSchemaVersion`。

### 5.6 禁止耦合

以下行为均不允许：

- 配置内容变化时提升 `configSchemaVersion`；
- 软件每次发布时无条件提升所有 schema/协议版本；
- 数据库加索引时提升事件 schema；
- IPC 新增命令时修改已提交事件；
- 用软件版本、Git 提交号或修改时间代替任一 schema/revision；
- 因未知新版本仍可被 JSON 解析就默认兼容。

## 6. 领域不变量

1. 业务相机身份只使用 `CameraId`，不依赖 IP；
2. 一个事件从 Candidate 到任一终态只有一个不可变 `EventId`；
3. Candidate 时立即保护缓存，不等待 Confirmed；
4. 事件判定、持久化、复核和上传状态互不替代；
5. 所有超时、时长和窗口只用单调时间；
6. 所有对外墙上时间都有明确 UTC/偏移，规范输出为 UTC；
7. 系统时间跳变不改变活动窗口和已有身份；
8. 配置 revision 与所有 schema/协议版本独立；
9. 已提交事件不原地改写；
10. 上传重试不创建重复事件或新的内容身份。
