# ADR-016：算法插件边界与进程内生命周期

- 状态：Accepted
- 日期：2026-08-04
- 决策者：项目架构基线
- 关联：M6-01、需求 4.7/4.9、架构 5.2/7～9

## 背景

M5 为打通事件链建立了只有 `process` 的 Mock 检测器接口。M6 需要在不改变采集和事件领域模块的前提下替换 Mock 与传统视觉实现，并统一初始化、热更新、重置、版本查询、错误隔离和耗时观测。

项目当前只批准同一 Windows 服务进程内的实现，也没有第三方算法 DLL 的发布、签名、兼容或故障隔离合同。直接导出含 STL、`std::chrono`、虚函数、异常和所有权类型的 C++ 接口，会把 MSVC 工具集、运行库、编译选项和依赖 ABI 变成未受控的外部契约。同步进程内调用也无法安全强制终止卡住的 C++ 插件。

## 决策

### 插件发现和 ABI

- M6 第一版采用进程内、编译期插件：实现与服务使用同一源码基线、MSVC v145、C++20 和动态 MSVC 运行库构建，通过组合根向 `DetectorPluginRegistry` 注册工厂；
- `IBreakDetector` 是仓库内部 C++ 模块边界，不是稳定的 DLL ABI，不通过 `LoadLibrary` 发现第三方实现；
- 接口只依赖 common、相机只读 `FrameView` 和算法领域类型，不暴露 MVS、OpenCV、Qt、SQLite 或 UI 类型；
- 注册表容量固定为 16，插件 ID 唯一；未知 ID、空工厂、工厂失败和异常均转换为稳定业务错误。

若以后确需独立升级或第三方插件，必须新增 ADR，优先评估版本化 C ABI 或进程外 RPC，并定义结构大小、调用约定、内存分配方、错误所有权、签名、兼容矩阵和崩溃恢复；不能把本 ADR 的内部 C++ 接口直接宣称为跨 DLL ABI。

### 生命周期和配置事务

`IBreakDetector` 提供：

- `initialize(DetectorConfig)`：将工厂创建的实例置为可处理状态；
- `process(FrameView)`：同步返回 `DetectionResult`；
- `update_config(DetectorConfig)`：应用更高修订号的同插件、同相机配置；
- `reset()`：清除帧间算法状态，不改变已应用配置；
- `info()`：返回插件 ID、实现/模型版本、热更新能力和原型标记。

宿主装载时只在“创建、初始化、信息校验”全部成功后替换活动实例。热更新不直接修改活动实例，而是：创建候选实例、用当前配置初始化、在候选上应用新配置、校验信息，最后交换。即使插件在失败前修改了候选内部状态，活动实例和旧修订仍保持不变。工厂应返回可初始化实例，`initialize` 对尚未处理帧的实例必须可重复调用，以兼容组合根的预构造验证。

`DetectorConfig` 的插件/相机 ID、修订号、处理预算和通用参数均有边界；参数不使用 JSON 或 OpenCV 类型。单个宿主绑定一台逻辑相机并由上层串行调用。本任务不创建线程或队列，M6-03 继续实现架构中已有的有界算法队列、排序、积压和降级。

### 异常、慢处理和指标

- 所有插件工厂和生命周期调用都位于宿主异常边界内，`std::exception` 与未知异常转换为 `ALGORITHM_PLUGIN_EXCEPTION`，不得逃逸到采集或事件模块；
- `process` 记录实际耗时、调用/成功/失败/超时计数和最大耗时；成功结果由宿主写入实测耗时及缺省实现/模型版本；
- 配置的处理时间是同步软预算。调用返回后若超过预算，宿主丢弃结果并返回 `ALGORITHM_PROCESS_TIMEOUT`；这能发现慢处理，但不能缩短已经发生的阻塞；
- 不创建分离线程、每帧 future 或无法确定关闭的任务来伪装硬超时。需要强制截止、崩溃隔离或终止失控算法时，必须采用经批准的进程外执行器及有界 IPC。

## 结果

正面结果：

- Mock 与后续传统视觉算法共享明确、可测试的生命周期和结果模型；
- 初始化/配置失败有宿主保证的强回滚，插件异常不会越过算法边界；
- 慢处理及版本可观测，事件模块继续消费兼容的触发结果，不依赖插件实现；
- 首版不承担不真实的跨 DLL ABI 或安全抢占承诺。

代价与风险：

- 热更新会创建并初始化候选实例，峰值期间同时持有新旧实例资源；未来模型实现必须在 M6-02/M6-03 记录并限制该预算；
- 软预算无法防止同步调用拖慢一个算法工作线程，M6-03 必须结合有界队列、跳帧、连续故障和降级指标；
- 编译期插件不能独立分发或不重启升级；若业务需要该能力，需重新评审 ABI 和安全边界。

## 被否决或推迟的方案

### 直接加载任意 C++ DLL

否决。当前没有受控 C ABI、工具链兼容、内存所有权、签名或崩溃恢复协议，把内部虚接口跨 DLL 暴露会形成脆弱且不可验证的 ABI。

### 在活动实例上原地热更新后尝试反向回滚

否决。插件可能在返回失败或抛异常前已部分修改内部状态，宿主无法证明反向调用能恢复。候选实例交换提供清晰的一致性边界。

### 每帧启动线程并等待超时

否决。C++ 无法安全杀死超时线程，分离线程会继续持有帧/插件并破坏有界资源和确定性关闭要求。首版诚实报告软预算，硬隔离推迟到经批准的进程外架构。

## 验证要求

- 未知插件、工厂失败/异常和初始化失败不产生活动实例；已有活动实例装载失败时保持不变；
- 热更新成功提高配置修订，更新失败或异常后旧实例仍以旧修订处理；
- 处理返回失败、标准/未知异常和超预算均成为稳定错误且指标准确；
- 重置成功、失败和异常均可测试，失败不销毁活动实例；
- Mock 实现信息查询、热更新和重置，既有手工/周期/灰度/ROI 测试不回归；
- 无实体相机测试不得被报告为硬件或正式算法验收。M6-00 未解除前 `prototype_only` 必须保持 true。
